# 13 · Hygiene — rules 13.1–13.7

*Read by path before any cleanup: a request to clean up, free space or remove stale builds, a close-out checkpoint, or a disk warning — and before you create a worktree, pause a lane, or answer which worktrees are stale. It does not load every session, and its `paths:` scope cannot fire for a worktree outside the project folder (a sibling `../<repo>-<lane>`, a snapshot in `/tmp`), so read it by path. It carries procedure; the authority stays in rules 10.1–10.2 (`DESTRUCTIVE.md`, always loaded): destructive acts need my OK, and they run alone, after validation.*

13.1 **Classify before you remove.** The class decides the action. When an item fits more than one class, the most protective one applies: protected, then evidence, then unknown, then the rest — so a log, report or database this session created is still evidence or protected, never scratch. A name (`tmp`, `old`, `backup`) or a `.gitignore` entry never decides it, because both describe intent, not what the item holds.

| Class | Examples | Action |
|---|---|---|
| **Regenerable and idle** | untracked or git-ignored toolchain output that a manifest or build command beside it rebuilds — `target/` beside `Cargo.toml`, `node_modules/` beside `package.json`, a `dist/` or test cache its build script recreates, `__pycache__/` | remove, alone, one directory per call, after checking no process uses it (your platform file gives the command); a tracked or hand-made folder of the same name is not in this class |
| **Disposable, created by this session** | the task's scratch files, a `mktemp` directory it made, a build target directory it created for itself outside the repository's own output folder, fixtures it built — nothing anyone has used since | remove when done, including a read-only inventory's own temporary files; a lane removes its own build target at its close-out and never leaves it for a later sweep |
| **Restorable by git** | local branches whose commits another branch or tag holds; worktrees that pass the checks in rule 13.3 | remove through git; a remote branch is outward-facing and not cleanup, and a tracked file is not cleaned up at all |
| **Evidence** | logs, reports, reviews, benchmark results, debug dumps a document refers to | keep; compress rotated logs (rule 9.4); archive large evidence only with its references updated |
| **Protected** | `.env`, credentials, keys, databases, state files, backups, anything I created | only on my word (rule 10.2) |
| **Unknown** | anything that fits none of the above | quarantine it (rule 10.3) — unless a running process uses it or it is a live database, which the quarantine procedure forbids moving: list it in the report instead |

13.2 **Remove only what is provably yours.** An item in rule 13.1's regenerable-and-idle class is the one exception: rule 10.2's build-output carve-out lets it go without an owner, and 13.1's row, not a folder name, decides membership. For everything else, proof is one of: this session created it, your lane holds its lock, or its marker (rule 13.4) names your task *and* your task's own record — its close-out report or handoff — lists the same path. What belongs to another lane, another agent, a running service or a person goes in the report (rule 13.5) and is not touched. A familiar name is naming, not permission (rule 9.2).

13.3 **Worktrees are removed through git, never by deleting their folder, and only after three read-only checks.**
    1. `git -C <worktree> status --short --ignored --untracked-files=all` — without the last flag an ignored folder collapses to one line and hides the `.env` or database inside it. Commit or quarantine uncommitted work first; after quarantining a modified tracked file, restore its committed version (`git -C <worktree> restore <file>`) — the content is safe in quarantine, and git refuses the removal until you do. Treat every git-ignored file that is not regenerable build output — a `.env`, a local database, a log — as protected: `git worktree remove` deletes ignored files silently, so preserve or quarantine them first.
    2. Its commits are reachable from a branch or tag: `git -C <worktree> for-each-ref --contains HEAD refs/heads refs/tags` must print a ref; its exit status is 0 either way, so the printed ref is the signal. A stash or a remote-tracking ref alone is not enough — one `git stash drop` loses it. A detached worktree's commits live on no branch, and removing it makes them unreachable, so branch or tag them first. The worktree's own HEAD log is deleted with it too: if `git -C <worktree> reflog` shows commits you moved away from and still need, branch them first.
    3. It is not in use: no running process works in it, and no other lane has it locked.

    Then run `git worktree remove <path>`, without `--force`, alone. If git refuses, fix the cause it names instead of forcing. `git worktree prune` clears the bookkeeping of worktrees whose folders are already gone, and skips locked ones. Deleting a worktree's folder with `rm`, or passing `--force`, skips git's checks and is a destructive act under rule 10.1. The lane that creates a worktree owns it — including a detached one made for a reviewer: it locks it with `git worktree lock` while it is in use, and its worktree is removed once its work is merged; rule 13.7 gives that lifecycle in full. Never remove a worktree another lane has locked. Delete a local branch only when another ref holds its commits: `git merge-base --is-ancestor <branch> <default>` succeeds, where `<default>` is the repository's default branch (`main`, `master`, `trunk`), or `git for-each-ref --contains <branch> refs/heads refs/tags` prints a ref other than `refs/heads/<branch>` itself — check 2 above cannot prove this, because a branch always contains itself. Then use `git branch -d`, which on its own is no proof: it refuses a branch not merged into its upstream, or into HEAD when it has none, and deletes a pushed branch that the default branch never merged. Never use `git branch -D` on a branch with unique work.

13.4 **Make things cleanable when you create them.** Put work products where their class is obvious: the task's scratch directory, a locked worktree, the toolchain's own output folder. A worktree's marker is its lock reason (rule 13.7), never a file inside it: an untracked file in a worktree makes `git worktree remove` refuse. Anything else large or long-lived you create elsewhere gets a marker file beside it, `.hygiene.json`, recording `owner`, `task`, `created`, `disposable` (`true` or `false`) and `regenerate` (the command that rebuilds it, or `null`). Cleanup reads the marker as the starting point of classification, not as its result. A marker never moves an item out of the protected or evidence class, whatever its `disposable` says. A marker you did not write, or cannot show you wrote, is evidence, not permission; rule 13.2 still applies. **Build output and large scratch never live on a memory-backed filesystem** (`/dev/shm`, any `tmpfs`, a RAM disk): that is not disk, it is the host's memory, and a build target left there outlives the lane and starves every other process — on 2026-10-16 a 44 GB cargo target in `/dev/shm`, idle for 26 hours, took a 94 GB machine to load 130 with its swap full. Check the filesystem type of a target path before pointing a build at it; your platform file gives the command. No room on disk means the disk needs this procedure, never that memory is the next disk.

13.5 **When hygiene runs, and what it reports.** Run it at every task close-out and phase end (rule 6.2's checkpoint), before work that uses a lot of disk, and whenever free space on the working filesystem falls below the floor — the one your local layer sets, or 10 % free when it sets none. **It also runs when memory is short:** whenever available memory falls below its floor — the one your local layer sets, or 10 % of the machine's memory when it sets none — or a memory-backed filesystem holds more than a quarter of its size; a large `shared` figure beside a small `available` one is the tell, and memory-backed items are the first candidates. Check free space, available memory, memory-backed filesystems and running processes first; your platform file gives the commands. Low space calls for this procedure, never for broader deletion. **The floor never stops work by itself:** below it, run this procedure, remove what is provably yours — build output by rule 10.1's route — report, and keep working. Stop only for a step whose measured need will not fit in the space left, and then say how much it needs and which candidates would free it. Every pass ends with a report: the worktree inventory (rule 13.7); what was removed, how, and the space reclaimed; what was kept, and why; and the next candidates for me, largest first, each with what would be lost and whether it can be regenerated. When I ask what to remove, answer in that same shape.

13.6 **A refusal ends the attempt.** When a guard or I refuse a removal, rule 10.1 applies: do not re-issue the same effect in another form — except rule 10.1's route for build output proven regenerable and idle, once, when the guard refused only the command's form. A refusal usually means the item was not provably in the first three classes. Reclassify it, then quarantine it or list it in the report as a candidate for me. **A refusal is not a classification:** it says that command was stopped, not that the item is protected. Build output proven regenerable and idle stays removable by rule 10.1's route, and a refusal recorded in a note or a handoff never turns it into something to keep.

13.7 **Every worktree is claimed, declared, and removed once it holds nothing git cannot give back.** Parallel lanes are welcome; a worktree nobody can account for is the defect. A worktree is cheap to make again — `git worktree add <path> <branch>` rebuilds one from its pushed branch — so once its contents are safe elsewhere, keeping it only costs disk and every later inventory.
    1. **At creation, the creator claims it:** `git worktree lock --reason "owner=<lane>; task=<task>; created=<YYYY-MM-DD>; state=running"`. The lock reason is the worktree's marker, written as `key=value` pairs so a script can read it; `git worktree list --porcelain` shows it beside the branch and HEAD. When the state changes, the owner re-locks it (`git worktree unlock`, then `lock --reason`) with the new `state=` and, for a pause, `since=`, `until=` and `why=`. A review snapshot is claimed the same way, by the lane that made it, and removed by that lane when its review is done.
    2. **When the task is done, the lane declares it; it does not remove it yet.** It commits everything, pushes, runs the task's checks, and reports to whoever runs the plan (rule 8.1's coordinator, or me): *ready to merge* — with the branch, the head commit and the evidence — or *not ready*, and why. It re-locks the worktree with `state=ready-to-merge` or `state=not-ready`. The close-out lists every worktree the task created and its state; a coordinator does not accept a close-out without that line.
    3. **An empty worktree may be removed by the coordinator at any time.** A worktree is **empty** when it holds nothing git cannot give back: its `HEAD` is contained in a pushed branch or tag (`git -C <worktree> branch -r --contains HEAD` prints one, and a local ref holds it too, per rule 13.3's check 2); `git -C <worktree> status --short --ignored --untracked-files=all` shows nothing but regenerable build output; no stash entry was made from it; and no process works in it. An empty worktree that is merged is removed — **a merged worktree is never left behind**: whoever merged it checks that its `HEAD` is an ancestor of the line it was made for (`git merge-base --is-ancestor <worktree HEAD> <target>`, the integration branch it feeds or the default branch), then unlocks and runs `git worktree remove`, without `--force`. An empty worktree that is not merged is removed too once it is not running and its branch and the `git worktree add` line are in the report or handoff; another lane's live lock still stops it (rule 13.3).
    4. **A paused or not-ready worktree stays while it holds work, and its cost shrinks on a schedule.** Nobody removes a worktree that is paused, not ready, or holds uncommitted work. The lane that pauses commits and pushes what it can and re-locks with `state=paused` and its `since=`, `until=` and `why=`. Then the coordinator, unasked:
        - reports it in every inventory, flagged once it is past its `until=` date or has none;
        - after the grace period — the one your local layer sets, or 7 days from `since=` — removes its build output (rule 13.1's regenerable class, by rule 10.1's route), unless your local layer marks that project's build folder as evidence;
        - after the stale period — past its `until=` date, or the one your local layer sets, or 30 days from `since=` when it has no `until=` — archives it: it commits and pushes any uncommitted work to `rescue/<branch>-<YYYY-MM-DD>`, quarantines (rule 10.3) any remaining ignored file that is not build output, such as a `.env` or a local database, compressed and with its manifest, and records the branch and the `git worktree add` line. The worktree is then empty and step 3 removes it.

        Deleting anything that is in neither git nor the quarantine — code above all — needs my consent; everything above preserves first, so it needs none.
    5. **A worktree whose lane died is adopted and handled by the coordinator, not swept and not parked for me.** When a worktree's lock names a lane that no longer runs — its session is gone and no process works in it — the coordinator takes the lane's authority over it: it re-locks it with `state=adopted; by=<coordinator>; from=<lane>; date=<YYYY-MM-DD>` and does what the lane would have done, because these checks are mechanical and the decision is the lane's own to make. First it preserves: uncommitted or unpushed work is committed to the lane's branch, or to `rescue/<branch>-<YYYY-MM-DD>` when it cannot tell whether the work belongs there, and pushed — never stashed, reset or deleted. Then it decides as the lane would: merged or empty → step 3 removes it; finished and its checks pass → it declares *ready to merge* (step 2) and the plan's merge proceeds; unfinished → it re-locks it `state=paused` with what is left, or finishes the task itself if the plan still wants it. Not merging is never deleting: an unmerged branch stays on the remote. It comes to me only for a conflict it cannot resolve, provenance or ownership it cannot establish, or a decision outside the plan.
    6. **The inventory answers "which worktrees are stale, and why keep them".** Every hygiene report lists all of the repository's worktrees from `git worktree list --porcelain`, each with its lock reason and the size of its build output, in five groups: **running**; **ready to merge**; **paused or not ready** — with `why=` and `until=`, flagged when past date or missing, and what step 4 did to it this pass; **merged or empty** — removed in this pass, or listed with what blocked it; **unclaimed or orphaned** — no lock, or a lane that no longer runs: adopted and handled under step 5, with what was done to each. Only what steps 4 and 5 send to me is listed for me. Another lane's live lock still stops you (rule 13.3): you list it, you do not remove it.
