# 8 · Subagents & model tiering — rule 8.1

*Read before dispatching any subagent or planning a fan-out. Which model fills each tier is `ROSTER.md` — read it with this file.*

*Local layer: if `~/.claude/rules/LOCAL_dev.md` exists, read it with this file — its entries for this section win over the wording here (section 0, "The local layer").*

*For supported task execution, agent/team messaging, and conditional Herdr communication, the source repository's `docs/guides/advanced-task-execution-and-communication.md` has examples; check the live harness before selecting a mode. The installed rules work without that guide.*

8.1 **Subagents & model tiering — coordinate approved plans in sub-agent mode, right-size the model, escalate fast.** For an approved multi-task plan, the main session coordinates scoped subagents for separable implementation lanes and independent reviews; name each lane's owner, files, deliverable, and integration boundary. Reach for subagents whenever work decomposes cleanly: independent pieces that can run in parallel, or large sub-tasks better kept out of the main session's context. This never overrides execution order — work that is sequential by workflow, or that shares code/files, stays sequential; only genuinely independent work runs in parallel. **Don't over-delegate, either:** if briefing and dispatching a subagent would cost more than just doing the task inline, do it inline — spawn overhead and orchestration tokens aren't free. If the harness offers no subagents, say so and execute the approved plan sequentially; never claim a lane ran when it did not.

    **The roster is `ROSTER.md`** — four tiers, **Top · Strong · Standard · Fast**, and the one file in the rulebook that says which model fills each. This rule names tiers, never models, so a model change is an edit to that file and to nothing here.

    - **Lowest capable model — except for planning.** Run each *implementation* subagent on the cheapest tier that can do its task: Fast for mechanical, fully-specified work; Standard for multi-file or integration work. The **Strong** tier is the escalation step between Standard and Top, and the tier that runs deep review (rule 3.1). Default low and let results — not habit — justify going higher. **Planning, design, and architecture ALWAYS run on the Top tier — never down-tiered, no matter how small the surface** (brainstorming, writing specs/plans, schema/API decisions, hard reasoning). A cheap plan is the most expensive mistake; the top model writes the plan, cheaper models execute it.
    - **"Lowest capable" is a floor, not a cap — up-tier on sight.** The orchestrator judges difficulty *before* dispatching: when a task is already visibly hard, start it higher rather than waiting for the cheap one to fail. Some domains **skip the Fast tier entirely and start on the Top tier** — complex or far-reaching architecture, anything touching **security** (auth/authorization, cryptography, trust boundaries, PII), **concurrency / memory models**, and systems-level or notoriously hard languages (**Rust**, C/C++, unsafe code, heavy type-level work). In these, a wrong cheap answer is more expensive than the model you saved on — give them power from the start. **Tier isn't the only knob — reasoning effort is the other:** for a borderline-hard task, first raise effort on the same model; jump a tier when the model itself, not its effort, is the limit.
    - **Review is not implementation, and it does not follow the same floor.** Mechanical review runs on the **Standard** tier, or on a model `ROSTER.md` qualifies for the mechanical review seat — never an unqualified Fast model, measured, see `ROSTER.md` — and deep review runs on the **Strong** tier (rule 3.1). An unqualified Fast model is thorough enough to be useful and not thorough enough to be a safety net.
    - **Escalate instead of flailing.** A subagent that stalls — stuck after a genuine attempt, looping, or about to guess — must stop early and move up a tier rather than grind. Put this in the init prompt of *every* subagent you spawn, e.g.: *"You are on the lowest model expected to handle this. If the task exceeds you — stuck after a real attempt, looping, or you'd be guessing — stop and reply `ESCALATE: <what is beyond you, and what you tried>` instead of continuing. Escalating early is cheaper than a wrong answer."* When a subagent returns that signal (or is otherwise blocked), re-dispatch the same task one tier up promptly — one escalation beats three dead-end attempts. **Carry the baton:** the re-dispatch must hand the higher model what the cheaper one already tried, found, and where it got stuck, so power isn't wasted re-deriving dead ends. **Ceiling, don't loop:** escalate one tier at a time — Fast → Standard → Strong → Top; if the Top tier is *also* blocked, stop and bring it to me with the evidence — never bounce the top model in a loop.
    - **Concurrency follows machine load, not ambition.** Before a fan-out, measure the host — **your platform file gives the three commands** (logical CPU count, current load, free memory) — and cap the number of *simultaneous* subagents to spare capacity. Derive the cap from cores × a load factor, where load = loadavg ÷ cores: near-idle (<0.3) → cores × 0.7, light (0.3–0.6) → × 0.5, medium (0.6–1.0) → × 0.35, heavy (>1.0) → × 0.2 — with a practical ceiling of ~20 and never more than free memory comfortably supports. On a 28-core box that lands near 20 / 15 / 10 / 5; on a 10-core laptop, near 7 / 5 / 3 / 2. Queued work still completes — only the concurrent count is bounded. If the runtime manages concurrency itself, defer to it but stay within these limits. Announce any large fan-out per rule 7.2.
    - **The planner is not the coordinator.** A long planner session that spends its context answering status questions does no development at all — that is the failure this split exists to prevent. The split: **the Top tier writes the plan** (deep, source-grounded) and **ends its turn**; a mid-tier **coordinator** runs the loop — dispatch, status, evidence, retries — and re-enters the planner for exactly three things: a plan revision, a review at deep depth, or a decision the coordinator can't make. A status check inside a planner session is a smell: hand it off or park. Where you have a task-board or coordinator tool, it holds the board and the briefs; where you don't, the coordinator is simply a separate session with the plan in hand.
    - **Know what actually contains a subagent, and don't confuse the controls.** An isolated working directory is **not** a sandbox. A worktree isolates *files in one repository*. A process sandbox limits *what the process can do*. A permission set limits *which actions are allowed*. They are three different controls, and only the ones your setup genuinely implements are real — an advertised capability is not evidence that it is enforced. Never describe one as another, and never widen what a subagent may do on the assumption that something else is holding the line.
    - **Scope & overrides.** This whole rule governs *ad-hoc* subagents you dispatch yourself. It does **not** apply to a purpose-built orchestration workflow with its own model and concurrency logic — when I invoke one of those, I mean it. And the model floor is for quality, never a cap on it: I can override **upward** anytime — name a stronger model, or freeze all work on a higher tier — and you hold that for the rest of the session until I lift it.
