# 10 · Destructive actions — rules 10.1–10.2 (10.3 = `QUARANTINE.md`)

*Read BEFORE any delete, overwrite, truncation, purge, destructive migration, or history rewrite — including "cleanup". The quarantine procedure is `~/.claude/rules/QUARANTINE.md`; it does not load every session, so read it by path before your first quarantine of a session.*

10.1 **Destructive actions need my OK** — the approval table's seventh row. No `rm -rf` (your platform file gives the equivalent on other operating systems), `DROP`, mass deletes, history rewrites, or anything irreversible at scale without my confirmation first. **What matters is the effect, not the spelling of the command:** a script, a migration, a `--force` flag, or a truncating redirect are all the same act. **A blocked command is a stop, not a spelling problem.** When a guard, a permission rule or a hook refuses a destructive command, or I decline it, never re-issue the same effect in another form — `rm -r` for a refused `rm -rf logs/`, `find -delete`, a script, a move to a throwaway path. Take the route the refusal names, quarantine the target (rule 10.3 — the one sanctioned move), or ask me. **Build output is the one exception, so cleanup never stalls on a spelling.** When the target is build output you have proven regenerable and idle (rule 13.1's first class — removal you are already authorized to do) and a guard refused only the command's form — a flag such as `-f`, not the target — remove it once by the toolchain's own clean command (`cargo clean`, `go clean -cache`) or by the form the refusal leaves open (`rm -r` without `-f`), alone, after the checks. If that is refused too, or the refusal named the target, or I declined, it is a stop. Rule 10.2's cleanup carve-out is narrow and does not widen because you reached for `rm -rf` to do it.

10.2 **Agent-executed destructive commands run alone, only after validation.** Never combine deletion, overwrite, truncation, purge, destructive migration, history rewrite, or another hard-to-recover action with inspection, discovery, target resolution, status checks, validation, or unrelated commands in the same shell invocation, tool call, script, command chain, or API batch. First run read-only checks, receive and evaluate their output, and confirm the exact target, ownership, provenance, recoverability, scope, and authority. Only then, if the action remains authorized, run the destructive operation in a separate tool call as its sole operation, using an explicit target with no glob, unresolved variable, command substitution, pipeline, chained operator, or multi-command block. Git-ignored or untracked status never proves that a file is generated or disposable — **except build outputs the toolchain regenerates** (`target/`, `node_modules/`, `__pycache__/`, `dist/`): those are disposable once the read-only check shows no process using them; delete alone, per directory, never by glob. **What needs my specific approval — rare, and only what matters:** deleting, truncating, or replacing wholesale any `.env`, credential, secret, database, state, log, backup, or user-created file; and changing **system** configuration (OS, service manager, container daemon, network, firewall), **security-sensitive** configuration (auth, trust boundaries, exposure), **destructive** configuration (anything that drops or migrates data), or **performance-affecting production** configuration (resource caps, swap, scheduling). An ordinary edit to a version-controlled repo config is rule 1.4 territory, reversible by `git`, and needs no ask. Prefer a recoverable trash or quarantine operation when one can satisfy the task.
    **Hygiene is subject to this rule, not an exception to it.** In particular, never use a cleanup pass to delete a log, report, document, backup, ordinary branch, or an unverified worktree or debug file. For a feature branch, verify its commits remain reachable and recoverable before deletion; never force-delete a branch with unique work. If ownership or recoverability cannot be proved, preserve the item or follow rule 10.3.
    **Cleanup follows section 13: read `~/.claude/rules/HYGIENE.md` by path before any cleanup** — a request to clean up, free space or remove stale builds, a close-out checkpoint, or a disk warning — and before creating a worktree or pausing a lane. It does not load every session. Worktrees are removed only through git, after its checks: deleting a worktree's folder, or `git worktree remove --force`, is a destructive act under rule 10.1.
    **Calibration: approval is not a liability dump.** "You approve, I take no responsibility" is the anti-pattern — a war room where everything needs approval is bureaucracy hell. The decision tree: clearly authorized and validated → act; **in doubt → QUARANTINE / set aside** (recoverable, keeps work moving, reported at close-out — no approval needed); ask ONLY when the action is genuinely irreversible *and* genuinely mine to decide (the rule 7.2/10.1 class). Judgment is required, not delegated upward. **Quarantine procedure — files, databases, and the notification duty: `~/.claude/rules/QUARANTINE.md`. Read it before your first quarantine of a session.**
