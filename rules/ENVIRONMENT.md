# 9 · Environment & operations — rules 9.1–9.7

*Read before claiming a port, touching a container, adding a datastore, handling logs or secrets, leaving anything running, or starting heavy work.*

9.1 **Ports:** before assigning a port, verify it's free — on the machine (your platform file gives the command) *and* against the claims registry at **`~/.config/agent-rules/ports/`** (one file per project). Claim your port by writing/updating your project's file there; also note it in the project README. Never reuse a conflicting port. (`~/.config/agent-rules/` is the machine-local registry home — sub-folders per concern; machine-specific gotchas live in `~/.config/agent-rules/machine.md`, not in these rules.)

9.2 **Docker:** name every container/volume/network with the project prefix (e.g. `myapp-api`, `myapp-db`), and give a throwaway test resource a run id you can recognise later. **A prefix is naming, not permission.** Anything without the prefix you do not stop, remove, restart, or modify unless I tell you to — and a matching prefix still isn't enough on its own: check that the thing is yours, from *this* task, before you touch it. Another run's container, an operator's, or a shared one can carry a familiar name. Export the logs you need before removing anything, and never remove data that isn't disposable.

9.3 **Datastores:** never introduce a native datastore — PostgreSQL, MySQL, Redis, etc. — unless I explicitly say so. Default to file/embedded options (config files, SQLite).

9.4 **Logs and durable evidence:** never delete, truncate, or wholesale replace log files unless I explicitly consent to the exact targets. Rotate logs without losing entries; compress only rotated or inactive logs after checking no process writes them, verify the compressed copy, and keep the original unless I explicitly consent to its deletion. Never compress an actively written log. Save logs, reports, documents, and guides as they are produced; never silently remove any of them during cleanup. Log files are preserved and `.gitignore`d by default, not auto-committed; commit a log only if I decide otherwise and its contents are reviewed for secrets and PII. Save and commit repository reports, documents, and guides in the normal close-out chain. If a log is retained outside the repository, report where it is. Rule 9.5 still forbids committing secrets or logging credentials/PII.

9.5 **Secrets:** never commit secrets, keys, or tokens. Secrets come from environment variables or a secrets store, never source. Never log credentials or PII. **Never print or echo a secret's value into the conversation — not even "just to look"; transcripts are archived.** Inspect secrets by name and presence. A length or a hash is a last resort, not a habit — a hash of a short or guessable secret is a lookup away from the secret. Never put one on a message bus or through a collaboration tool. **Reading a log is a secret surface:** strip terminal colour codes first, then mask every URL down to its host and any run of 30 or more token-like characters before a line is printed — a credential travels inside a URL path as easily as in a `key=` assignment (2026-10-17: a bot token 35 characters long, in a `/bot<id>:<token>/` path, passed a 40-character mask and reached a transcript). Prefer counts and timestamps over message bodies.

9.6 **Long-running processes: nothing keeps running silently.** Anything started that outlives the task — containers, soak tests, watchers, dev servers — is either stopped at close-out or explicitly reported as left running, with the reason and the exact teardown command.

9.7 **Heavy work measures the host first, and a green host starts at once.** Before a build, a full test suite, a fan-out, or anything else that will load the machine for more than a moment, measure the host — load, available memory, and what memory-backed filesystems hold; your platform file gives the commands. Read the load as a factor, load ÷ cores, so the bands hold on any machine; your platform file says how to read it where there is no load average, and your local layer may state the bands as absolute numbers for one box. **Green, below 0.9, with memory above rule 13.5's floor: start now.** The measurement is the whole of this rule's cost on a quiet machine; a green host is never a reason to wait, and this rule never asks anyone's permission. **Orange, 0.9 to 1.8:** nothing new and heavy starts; what is running finishes. **Red, 1.8 and above, or available memory below rule 13.5's floor:** a running lane pauses before its next heavy step too, and nothing starts until a fresh measurement is out of the red. **Waiting is only for orange and red, and it is a wait, not a stop:** re-measure and start the moment the host is green. A lane that is already running measures again before each heavy step and pauses when the host has gone heavy under it — the fan-out that measured a quiet machine is not the one running now. Where the host has a shared lease for heavy work, take it before building. **The number that decides is the one you read now:** run the command at the moment of the decision — before each heavy step, and again whenever you resume after a pause or an interruption — and read the 1-minute average. A figure already in the conversation is a record of an earlier machine, not a measurement, and the 5- and 15-minute averages are history after a spike (2026-10-16: a lane resumed after a pause and declined a gate on a host at load 2.5, because the 134 it had read before the pause was still in front of it). Say in the close-out when the measurement changed what you did. A machine at load 130 on 28 cores with its swap full is not a reason to start a fourth compile; it is the reason to stop the third (2026-10-16: four lanes compiled at once on a box that had been at 3 GB free for a day, and none of them had looked).
